You are generating a Business Requirements Document (BRD) following INT's
Specification-Driven Development (SDD) methodology.

## Source Input

Read the Statement of Work (SOW).

## Task

Create a brand-new file at .ai-context/BRD.md — do NOT edit, append to, or
merge with any existing BRD.md. If a file already exists at that path, treat
this as a full replacement (overwrite), not an addition.

## Discovery Rules (per sdd-methodology.md #7)

Before writing any entry, complete discovery for each distinct business need
found in the SOW:

- Confirm the underlying business need, not just the literally requested
  feature — flag it explicitly if the SOW's wording and the real need diverge.
- Separate what is already decided (explicit in the SOW) from what is still
  open (ambiguous, unstated, or left to a future decision-maker).
- Do not invent decisions the SOW doesn't make. If something is unresolved,
  it belongs in "Open at BRD stage," not silently assumed.
- Do not write anything into the BRD that isn't traceable back to a specific
  part of the SOW — no speculative scope.

## Output Format

Produce one numbered entry per distinct business requirement/need identified
in the SOW, using this exact structure for each:

### BRD-<NNN>: <Short title>

**Raised by:** <source/sponsor, inferred from SOW if named, else "SOW — not specified">
**Business need:** <1-3 sentences, the underlying problem/outcome, not the feature ask>
**Sponsor:** <owner/accountable party if named in SOW, else state "Not specified in SOW">
**Priority:** <High/Medium/Low, with a one-line justification if inferable, else "Not specified in SOW">
**Decided:** <what the SOW explicitly commits to — constraints, chosen approach, integrations, etc.>
**Open at BRD stage:** <anything ambiguous or unstated that must be resolved before spec drafting — be specific, not "TBD">
**Notes:** <scope boundaries, explicitly excluded items, dependencies on other BRD entries, or anything future-phase>

Number entries sequentially starting at BRD-001, in the order the underlying
needs appear or are most naturally grouped in the SOW.

## Quality Bar

- Each entry must pass the test in sdd-methodology.md #7: "what problem, for
  whom, bounded how" answerable in one paragraph. If you can't answer that
  for a candidate entry, it's not ready to write — split it, or flag it as
  an open question instead of forcing an entry.
- Do not merge unrelated needs into one entry to save space, and do not
  fragment one need into several entries just to inflate the count.
- No PII, secrets, or client-confidential data (per constitution rules) —
  reference roles/functions, not named individuals, unless the SOW itself
  names a role holder as sponsor.
- Flag anywhere the SOW is silent on something a BRD entry would normally
  need (sponsor, priority, decided-vs-open) rather than guessing.

## Deliverable

A single new .ai-context/BRD.md file containing:

1. A one-line header: `# Business Requirements Document` and a
   `_Source: <SOW filename>, generated <date>_` line.
2. All BRD-NNN entries in the format above.
3. A closing "## Coverage Note" section listing any parts of the SOW that
   did not translate into a BRD entry (e.g., purely commercial/contractual
   terms, timelines, out-of-scope statements) and why they were excluded.
