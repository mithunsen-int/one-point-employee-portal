Create the following seven files under .agent/workflows/ in this repo. These
are reusable prompt templates for an AI-first SDD methodology (see
sdd-methodology.md, which must already be in this repo — read it in full
before writing anything, since every file below must reference specific
section numbers from it, not paraphrase them).

Read sdd-methodology.md sections #5, #7, #8, #9, #10, #11, #12, #13, #14,
#16, #18, #19, #21, #28, #29, #30 before starting. Also read constitution.md,
BRD.md, project_context.md, and the project's actual stack-standards file
in .agent/rules/ (e.g. int-standards.nextjs.md) so the workflows reference
the real datastore (MongoDB via Mongoose) and stack conventions already
decided for this project, not generic placeholders.

FORMATTING RULES — apply identically to all seven files, no exceptions:

- Title line: "# Workflow: /<workflow-name>" (with the leading slash).
- Immediately below the title, one blockquote line starting
  "> **Methodology reference:**" naming the specific sdd-methodology.md
  section numbers this workflow enforces.
- "Purpose" and "Usage" are NOT headers — write them as bold inline
  labels directly in a paragraph, e.g. "**Purpose:** ..." and
  "**Usage:** \`/workflow-name <arg>\`" (usage as inline code, not a
  fenced code block, unless it genuinely needs multiple lines).
- All other sections ARE level-2 headers in sentence case exactly:
  "## Preconditions", "## Steps", "## Output", "## Do not" (lowercase
  "not" — do not title-case it).
- Preconditions and Do-not sections are numbered or bulleted lists.

1. generate-spec.md — Drafts .ai-context/specs/<feature-slug>.spec.md
   from a .ai-context/BRD.md entry, per #11.4's template.
   - Usage: `/generate-spec <BRD-#>` — a single parameter only, the source
     BRD entry's own ID (e.g., BRD-007). The workflow locates that entry
     directly by ID, then determines the resulting feature-slug itself:
     reusing one already associated with this BRD entry elsewhere in the
     project (an existing spec's "Linked BRD" field, or a row in
     status.md) if one exists, otherwise deriving a fresh slug from the
     entry's title per #9's rules.
   - Must stop if no entry with that ID exists in BRD.md (#7).
   - Must check .ai-context/discovery-analysis.md for open items relevant
     to this feature and stop if an unresolved item would need to be
     guessed to draft an AC.
   - Must never set Status to Approved itself — only Draft v1.0, since
     Gate 1 is a human review this workflow cannot complete.
   - Must clarify that the spec's own Unit Test Cases table is the
     acceptance-level minimum only — broader QA scenarios belong in the
     separate generate-test-cases workflow, not duplicated here.
   - Where constitution.md states a constraint is not yet set, the spec
     must say the same rather than inventing a number.
   - Output should include a short self-check summary (which sections
     are fully populated vs. carry an explicit "not yet set"/"deferred"
     note) — not a Gate 1 verdict, since only a named human reviewer can
     issue one.

2. generate-plan.md — Drafts .ai-context/plans/<feature-slug>.plan.md
   from an Approved spec only (#13).
   - Usage: `/generate-plan <feature-slug>`
   - Must stop and refuse if the spec's Status isn't Approved.
   - Must produce a literal Constitution Check checklist (checked with a one-line justification, never blindly ticked).
   - Must make the rate-limit decision explicit for every endpoint, even if the decision is "none, deferred."
   - Must flag if a new datastore/service would need an ADR rather than silently deciding architecture.

3. generate-tasks.md — Generates .ai-context/tasks/<feature-slug>.tasks.md
   from the plan's Sequencing section (#10 Step 3), one task per
   sequencing step, each with a stable <feature-slug>.T0# ID and an
   explicit "Acceptance: <AC IDs>" line.
   - Usage: `/generate-tasks <feature-slug>`
   - Must also generate one standalone prompt file per task at
     prompts/<feature-slug>.T0#.prompt.md, following prompt-by-identity
     discipline (#16) — referencing IDs, not re-describing the feature
     from memory, and explicitly stating what NOT to touch (sibling tasks,
     out-of-scope files).
   - One task, one prompt file — never batch multiple tasks into one prompt.

4. generate-tests.md — Writes the actual failing (Red) test CODE for one
   named task, before implementation exists (#5 non-negotiable #3,
   test-first).
   - Usage: `/generate-tests <feature-slug>.T0<n>`
   - Must stop if implementation code for that task already exists (retrofitting tests is a listed anti-pattern, #28).
   - Must pull test scenarios from both the spec's own Unit Test Cases table AND the QA-expanded test_cases/<feature-slug>.test_cases.md file.
   - Must confirm and record that every new test fails for the expected reason before stopping.

5. generate-test-cases.md — A SEPARATE workflow from generate-tests.md
   (different purpose, don't conflate them).
   - Usage: `/generate-test-cases <feature-slug>`
   - Expands a spec's Unit Test Cases table into the QA-owned documentation table at .ai-context/test_cases/<feature-slug>.test_cases.md — data variations, negative paths, boundary cases, role-matrix sweeps.
   - Where the correct expected behavior is genuinely ambiguous, this workflow must NOT guess — it records the item under an "Open QA Questions" section instead, routing it back toward a spec amendment.

6. code-review.md — Runs the Gate 2 code-review pass over one task's
   diff (#30's Gate 2 checklist + Security checklist, both applied in
   full, every item, every time).
   - Usage: `/code-review <feature-slug>.T0<n>`
   - Records the outcome as an appended row in .ai-context/gate-reviews/gate2-evidence-<feature-slug>.md — one running evidence file per feature, not one file per task.
   - Must flag any AI-attribution in comments/commits (prohibited) while confirming task-ID references like "Implements <feature-slug>.T03" are fine.
   - Must explicitly state that the AI may draft this review, but only a named human reviewer can mark a task Merged (#5.7).

7. generate-gate1-review.md — Records an already-completed Gate 1 reviewer's verdict
   into the spec, a running evidence file, and status.md, per the fixed
   10-item checklist structure defined in the workflow itself (#12, #12.3).
   - Usage: `/generate-gate1-review <feature-slug>`
   - Must require the reviewer's name and their actual pass/fail
     determination on all 10 checklist items to already be supplied by
     the invoker — this workflow never performs the review or generates
     findings itself (#12.1).
   - Must refuse if the named reviewer is the spec's own author (#12.1).
   - Must refuse to record a verdict on a partial (fewer than 10 items
     resolved) checklist.
   - On `Approved`, sets the spec's Status field to Approved. On
     `Changes Requested`, leaves Status at its Draft version and notes
     that the author must bump to the next minor version (e.g.
     Draft v1.1) upon revision, per #12.3.
   - Writes to .ai-context/gate-reviews/gate1-review-<feature-slug>.md —
     one running file per feature for this gate; a resubmission after
     Changes Requested appends a new dated round rather than overwriting
     the prior one.
   - Must update .ai-context/status.md's Active Specs row and Daily
     Execution Log to match the recorded outcome.

Do not implement any application code, tests, or specs while creating
these seven files — this prompt produces only the seven workflow template
files themselves, and all seven must follow the FORMATTING RULES above
identically.
