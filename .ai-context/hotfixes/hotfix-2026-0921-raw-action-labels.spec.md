## What Was Broken
Both Admin and Stakeholder panels' request detail screens render each Action History entry as `{actor} — {action} — {timestamp}`, where `action` is the *raw, internal, snake_case* string passed to `recordTransitionAudit` at each workflow transition (e.g. `manager_approved`, `payroll_task_completed`) — never translated into human-readable text anywhere in the render path. A user reading their own request's history sees system identifiers, not a description of what happened.

## Root Cause
Confirmed directly against the code, not assumed: `RequestDetail.tsx` (stakeholder-panel-ui) and `TransferRequestDetail.tsx` (admin-panel-ui) both interpolate `entry.action` straight into JSX with no lookup/formatting step. This was never caught by either screen's own Gate 2 review because every existing test asserts on the *presence* of the action string (`getByText(/submitted/)`, etc.), which passes equally whether the string is raw or humanized — the tests never asserted on the *label's readability*, only its existence, so a raw key satisfied them without exposing the gap. There are exactly 9 distinct raw action values in the system today (grepped every `recordTransitionAudit(...)` call site): `submitted`, `manager_approved`, `manager_rejected`, `hr_approved`, `hr_rejected`, `payroll_task_completed`, `it_task_completed`, `facilities_task_completed`, `hr_final_mapping`, `withdrawn` (`withdraw`'s route also records `withdrawn`) — 10 total, all snake_case, all currently shown verbatim.

**Explicitly out of scope for this hotfix, and why:** the `status` field (`"Pending: Manager"`, `"Pending: HR"`, etc.) is *not* a raw system key — it's already the exact human-readable vocabulary `internal-transfer-workflow.AC18` deliberately specifies, title-cased with spaces. Also out of scope: the several places this project *deliberately* surfaces a raw error code on a form (e.g. `username_exists`, `admin_already_exists`) — those were explicit, reviewed, tested Gate 2 decisions in multiple already-Merged tasks ("a duplicate-username 4xx... displayed on the form via Formik's status, not silently dropped"), a different category of decision than an unreviewed oversight, and reversing them isn't what the user asked for. This hotfix is scoped exactly to the Action History `action` field, the only place matching the user's own examples.

## Correct Behaviour (Acceptance Criteria)
1. Given any Action History entry, when it is rendered on either panel's request detail screen, then a human-readable label is shown instead of the raw action key (e.g. `manager_approved` → "Approved by Manager", `payroll_task_completed` → "Payroll task completed") — for all 10 known action values.
2. Given an action value that doesn't match any known mapping (defensive case — e.g. a future transition added without updating the label map), then the raw value is still shown rather than the screen crashing or the entry disappearing silently — a graceful fallback, not a hard failure.
3. Every existing test in both `RequestDetail.test.tsx` and `TransferRequestDetail.test.tsx` still passes — this is a display-mapping change only, no change to what data is fetched, stored, or which entries appear.

## Fix Summary (planned, not yet applied)
Add one new shared module — `src/shared/workflow/actionLabels.ts` — exporting a single `actionLabel(action: string): string` function with a literal lookup table for all 10 known values, falling back to the raw string for anything unrecognized (AC2's graceful-degradation requirement). Both `RequestDetail.tsx` and `TransferRequestDetail.tsx` import this one function and call `actionLabel(entry.action)` instead of interpolating `entry.action` directly — a shared module because both panels display the exact same underlying data (per `RequestDetail.tsx`'s own existing comment, "Same underlying data as `transfer-audit-trail.API02`"), so the mapping must not be duplicated and drift between the two screens. No backend change — `recordTransitionAudit`'s stored values stay exactly as they are (the raw key remains the correct, stable value to persist and audit; only its *display* changes). Respects `constitution.md`: no new dependency, no datastore change, no PII touched, test-first discipline applies to the fix itself (new Red tests asserting the humanized label appear before the mapping is added, existing tests re-confirmed unmodified after).
