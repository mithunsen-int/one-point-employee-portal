# CLAUDE.md

Operating rules for Claude Code in this repository. This file summarizes `.agent/rules/sdd-methodology.md` — it does not replace it; section numbers below (`#7`, `#9`, etc.) point back to that file, read it directly for full detail before an ambiguous call.

_Also see `AGENTS.md` in this same directory — it's auto-maintained by `next dev` itself and carries Next.js version-specific guidance (this install may have breaking changes vs. training data; check `node_modules/next/dist/docs/` before writing framework code). That file regenerates on its own; this one doesn't._

## The one rule that overrides convenience

**Never vibe-code.** Do not write or edit application code, and do not draft a spec, plan, task, or test, on any branch that will be reviewed, merged, or demoed — without going through the artefact chain below. Exploratory local spikes are the only exception, and they graduate to a spec the moment they show promise (**#28**).

## Non-negotiables (sdd-methodology.md #5 — every task, no exceptions)

1. No implementation task runs without an **Approved** spec, approved by a named peer reviewer who is not the author.
2. Stop vibe coding — no spec-less prompting against a reviewed/merged/demoed branch.
3. Test-first — no implementation code before the corresponding test exists, is reviewed, and is confirmed **Red**.
4. The spec is the contract. No AI-attribution in comments or commit messages, ever — a task-ID reference (e.g. "Implements `<feature-slug>.T03`") is traceability, not attribution, and is expected, not just permitted.
5. Secrets and PII never enter a spec, plan, task, or prompt log.
6. Context is scoped, not dumped — feed only the spec/plan/referenced modules for the current task, never the whole repo.
7. A human is accountable for every merged line. "The agent wrote it" is never a valid defense in review, production, or postmortem.

## The artefact chain

```
BRD → Spec → Gate 1 (human peer review) → Plan → Constitution Check → Tasks
   → Test-first (Red) → Guided Implementation (Green) → Gate 2 (human review) → Merge
```

Use the matching `.agent/workflows/` template for each step instead of freehand prompting (**#16**). This project does not use slash commands — each step is invoked by referencing its prompt file directly and stating the argument after "for," e.g. `@generate-plan.md for <feature-slug>` (prompt files live in `prompts/`, one per workflow, each just pointing at the real logic in `.agent/workflows/`):

| Prompt file | Does | Cannot do |
|---|---|---|
| `@generate-spec.md for <feature-slug>` | Drafts a spec from a BRD entry it locates itself | Never sets Status past `Draft v1.0` |
| `@generate-plan.md for <feature-slug>` | Drafts a plan, with a literal Constitution Check | Refuses unless the spec's Status is `Approved` |
| `@generate-tasks.md for <feature-slug>` | Decomposes the plan's Sequencing into `<slug>.T0#` tasks + one prompt file each | Refuses if the plan's Constitution Check has an open gap |
| `@generate-tests.md for <feature-slug>.T0<n>` | Writes failing (Red) tests for one task, before implementation | Never writes implementation code |
| `@generate-test-cases.md for <feature-slug>` | Expands QA scenarios into `test_cases/` (separate from generate-tests) | Never writes executable test code |
| `@code-review.md for <feature-slug>.T0<n>` | Runs the Gate 2 + Security checklist, appends evidence | Never marks a task Merged |
| `@gate1-review.md for <feature-slug>` | Records an already-completed Gate 1 reviewer's verdict + findings into the spec, `gate-reviews/`, and `status.md` | Never performs the review or picks the verdict itself; refuses if reviewer name = author |

None of these workflows can grant Gate 1 or Gate 2 approval on their own judgment. `gate1-review` does write `Approved`/`Changes Requested` to the spec's `Status` field, but only as a literal transcription of a verdict a named human reviewer has already stated out loud — never as this agent's own assessment. `code-review` never flips a task to `Merged` under any circumstance — that stays a manual human action outside any prompt file here.

## Repository map (sdd-methodology.md #15)

```
.agent/
  rules/      → sdd-methodology.md, int-standards.<stack>.md, auto-log.md, .agentignore
  workflows/  → the real logic for the seven prompt files above
prompts/      → one thin @-mentionable prompt file per workflow (no slash commands in this project);
                also holds per-task prompt files (<feature-slug>.T0#.prompt.md) generated by generate-tasks
.ai-context/
  constitution.md        → project non-negotiables (#8) — check every plan against this line by line
  BRD.md                  → where a requirement is first written down (#7)
  discovery-analysis.md   → full discovery record BRD.md's entries are formalized from
  project_context.md      → one-page orientation
  architecture.md         → living system design — keep current or don't trust it (#17)
  status.md                → state & progress board (#21) — update same day, never let it go stale
  specs/, plans/, tasks/, test_cases/ → per-feature artefact chain, named by slug (#9)
  gate-reviews/            → Gate 1/Gate 2 evidence, one running file per feature per gate
  decisions/               → ADRs, project-global sequential IDs
  changed_requests/        → lightweight, spec-styled write-ups for a real gap or improvement (e.g. found during
                             Gate 2) that isn't a defect (so no hotfix/bug-fix spec) and isn't ADR-significant
                             (so no ADR) — parked here as Status: Proposed until picked up as a real task
```

## Naming (sdd-methodology.md #9)

- Feature slug: kebab-case, 3–5 words, verb-free, unique for the project's life (e.g. `2fa-otp-login`, not `login-fix` or `feature-2`).
- Sub-IDs scoped under the slug: `<slug>.AC#` (acceptance criteria), `<slug>.API0#` (endpoints), `<slug>.UT0#` (spec-derived tests), `<slug>.T0#` (tasks).
- ADRs get project-global sequential IDs (`ADR-00NN`), never scoped to a slug.
- **Prompt by identity, not description** (**#16**) — "Implement `<feature-slug>.T03`" survives a spec revision; "implement the rate-limiting task" doesn't.

## Hard stops — refuse and say why, don't route around

- No BRD entry exists for a requested feature → do not draft a spec; ask for one to be authored first.
- Spec Status isn't `Approved` → do not draft a plan.
- Plan's Constitution Check has an unresolved gap → do not generate tasks.
- Implementation already exists for a task → do not retrofit tests; flag the anti-pattern (**#28**) instead.
- An acceptance criterion or NFR value isn't stated anywhere in BRD / `discovery-analysis.md` / `constitution.md` → do not invent one; report the gap instead.

## Do not

- Do not implement, or ask for, more than one task's worth of change per prompt/session (**#16** — "one task, one prompt").
- Do not attribute AI authorship in code comments or commit messages — task-ID references are fine and expected.
- Do not add to `.ai-context/specs/`, `plans/`, `tasks/`, or `test_cases/` outside the `generate-*` prompt files and their preconditions.
- Do not mark any task Merged, or any spec Approved, on this agent's own judgment (**#5**, Principle 7). `gate1-review` may write `Approved` to a spec's `Status` field, but only when transcribing a verdict a named human reviewer (not this agent, not the spec's author) has explicitly stated — never as a judgment this agent forms itself.
